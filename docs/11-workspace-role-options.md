# 邀请式使用与内部内容建设权限

日期：2026-10-10。仅评估方案，未修改账号、角色、工作空间、网关或沙箱配置。[所有权交接方案](10-partner-ownership-plan.md)仍待确认，尚未执行。

## WeKnora 原生账号与成员模型

已通过本地 Git 标签 `v0.8.2` 对照，基线提交为 `3e8b0bfc`。以下说明针对本仓库所采用的基线，不代表其他版本的全部行为。用户、成员角色、普通邀请路由、知识库及 Agent 路由的相关核心文件与该基线一致；新增团队负责人授权不属于原生四级角色。

| 概念 | 原生含义 |
| --- | --- |
| 用户账号 | 一个人的登录身份，包含邮箱、密码和显示名；公司名称不是另一个人的账号 |
| 工作空间 | 团队资源和成员权限的主要边界，容纳知识库、Agent、技能及配置 |
| 空间成员 | 连接用户与工作空间的成员记录；同一用户可以加入多个空间，各自持有不同角色 |
| 知识库 | 空间内的资料集合；不是独立的用户登录身份，不能把创建人字段当作逐用户阅读名单 |
| 组织共享 | 将指定知识库或 Agent 分享给其他成员工作空间；组织的成员单位是空间，不是个人 |
| 系统管理员 | 独立的平台权限，用于账号、平台设置等管理，不等同于某个空间的 Owner |

原生默认设置支持公开注册，并默认创建个人空间、让注册人成为 Owner；也支持关闭公开注册、仅邀请，以及注册后暂不分配空间。我们当前采用邀请制，并关闭普通用户自建空间，所以当前页面与上游默认体验不同。这些设置来自原生能力，并非为了伙伴另建了一套账号系统。

创建空间时，创建人默认取得该空间 Owner。Owner 可以按邮箱邀请已注册账号，或创建邀请链接供新用户注册/已有用户加入；原生邀请可指定有效角色，接受后建立成员关系。普通成员邀请、角色调整和成员移除的真实路由要求 Owner，不能依据部分配置描述中的“Owner/Admin”推断 Admin 也能操作。

| 原生空间角色 | 核心能力 |
| --- | --- |
| Owner／所有者 | 管理空间、成员、角色、普通邀请及空间 API Key；空间不能没有有效 Owner |
| Admin／管理员 | 管理空间资源和多种集成配置，管理原生 Skill；普通成员邀请不由此角色授予 |
| Contributor／贡献者 | 创建知识库和 Agent，通常维护自己创建的资源；不是私有阅读空间 |
| Viewer／只读成员 | 阅读资料、发起问答和使用已授权能力，不获得资源创建或普通邀请权限 |

切换空间只改变同一登录用户的工作上下文；“星辰教育／刘伟健·所有者”意味着刘正在星辰空间，并没有切成卡卡。邀请某个人不会把两个登录账号合并，也不会自动赋予邀请者对该人员其他空间的权限。

| 当前能力 | 原生或定制 |
| --- | --- |
| 账号、空间成员、四级角色、普通邀请及空间切换 | 原生 |
| 邀请制、关闭自建空间、开启 RBAC | 原生配置能力，当前部署已采用相应策略 |
| 总部一键创建伙伴空间并安装预设 | BoyanKB 定制；执行开通的管理员被保留为伙伴 Owner |
| 卡卡保持 Viewer 却能邀请只读员工 | BoyanKB 定制的指定团队负责人能力；原生 Viewer 不能普通邀请 |
| 三位受管 Agent、九项业务技能及受控文件生成 | BoyanKB 定制；不等同原生任意 Skill 的上传和沙箱安装 |
| 公网屏蔽原生 Skill、沙箱和平台管理入口 | 当前试用部署策略，不代表上游没有这些接口 |

核查依据为基线中的 `internal/types/{user,tenant_member}.go`、`internal/router/routes_auth_tenant.go`、`internal/handler/tenant.go`、`internal/application/service/system_setting.go`。与基线相比，`internal/application/service/tenant_invitation.go` 增加了定制团队邀请接受时的权限复核；`internal/teaminvitation/`、`internal/businessworkflow/team.go` 和 `internal/application/service/partner_provisioning.go` 为新增实现。本轮没有运行上游原版实例，默认界面体验为源码结论，端到端运行未验证。

## 是否需要所有权交接

合作伙伴可以作为受邀成员加入工作空间，使用获授权的知识库、智能体和业务技能，不需要成为所有者。现有卡卡账号已经是此模式：星辰教育 Viewer，并额外获得受限的团队负责人邀请能力。

邀请式使用与总部管理员能否进入伙伴空间是两件事。刘伟健保留伙伴 Owner 就仍然能够切入；之前的交接方案用于满足“刘伟健账号也不得进入伙伴空间”的额外约束，并非合作伙伴使用系统的必要条件。没有得到新的决定前，不执行交接，也不将本轮讨论视为已撤销这一约束。

## 工作空间组织方式

| 组织方式 | 适用条件 | 当前限制 |
| --- | --- | --- |
| 一个内部空间＋一个伙伴公共空间 | 全部伙伴使用相同的公共资料和智能体，成员由总部统一邀请 | 知识库、智能体和成员名单不按公司隔离；当前负责人绑定不能支持每家公司分别管理员工 |
| 一个内部空间＋每家公司一个伙伴空间 | 伙伴负责人需自行邀请本公司员工，且伙伴之间需隔离 | 需要维护空间成员关系，但各空间可共享同一企业知识库，不复制资料 |

结合此前“卡卡能够邀请员工、伙伴之间隔离”的要求，建议沿用第二种方式。伙伴仍只是受邀使用者，Owner 由总部管理身份或独立运维身份承担，是否交接刘伟健权限另行确认。

“工作空间”是成员和权限边界，“知识库”是其中的资料集合。当前普通网页用户的同空间知识库/智能体读取没有逐用户或部门的独立 ACL：知识库访问见 `internal/application/access/knowledgebase.go:117`，智能体列表见 `internal/application/repository/custom_agent.go:43`。不能将内部员工新建的机密知识库放在伙伴也加入的同一个空间，再依赖名称、创建人或提示词隐藏。

原生成员列表接口允许 Viewer 查询，见 `internal/router/routes_auth_tenant.go:112`。现有业务团队页的展示过滤不能代替此接口的权限边界。普通网页聊天按当前用户隔离，但历史无用户归属的会话、API/IM/embed 管理视图另有规则；合并空间前仍须检查历史数据，不能承诺共用空间后所有旧内容都自动按个人隐藏。

企业飞书知识库可以继续只有一份，由内部空间向伙伴空间以只读方式共享；只分享明确获准的库或智能体。新建内部知识库不自动纳入对外共享。通过共享智能体也可能提供其绑定知识库的读取权限，发布时必须核对关联库范围。

## 内部员工权限

| 人员 | 建议空间角色 | 创建知识库 | 创建 Agent | 原生 Skill 管理 |
| --- | --- | --- | --- | --- |
| 普通内部使用者 | Viewer | 不允许 | 不允许 | 不允许 |
| 内部内容建设者 | Contributor | 支持 | 支持 | 不允许直接上传/安装 |
| 内部技能维护者 | Admin，仅授权内部空间 | 支持 | 支持 | 原生 API 支持上传、安装和删除，但当前部署入口与执行条件尚未开放 |
| 空间负责人 | Owner | 支持 | 支持 | 同 Admin，并承担成员和空间授权管理 |
| 外部伙伴、员工 | Viewer；伙伴负责人另加受限邀请绑定 | 不允许 | 不允许 | 使用已发布业务技能，不管理或安装原生 Skill |

知识库和 Agent 创建由 Contributor 门禁控制，见 `internal/router/routes_knowledge.go:204`、`internal/router/routes_agent.go:38`。普通资源更新/删除还检查创建者或管理员，因此“能创建”不等于可以修改同事全部资源。反过来，历史创建者即使降成 Viewer，部分归属授权仍可能允许维护其旧资源；从内容建设者转为严格只读人员时，需要审查原有资源归属，不能只改角色。

空间 Admin 不是平台 SystemAdmin，但仍能管理本空间较多资源。如果希望某位员工只能发布 Skill、不能管理其他人的知识库和 Agent，现有角色不够细，需要新增独立能力或采用提交后由管理员发布的流程，不直接给出范围过大的 Admin 权限。

## Skill 的现状与最小改造方向

原生 Skill 的目录上传、安装、内容读取和删除要求 Admin，见 `internal/router/routes_agent.go:86`。它采用 Skill 包/目录和安装流程，不等同于在聊天框写一句提示词就创建成功。

当前公网试用网关明确屏蔽 `/api/v1/skills/*`，沙箱接口也被拒绝，且工作空间禁用了通用脚本。因此现在只提升内部员工角色，仍不能通过公网上传、安装和执行任意原生 Skill。此结论来自实际部署配置 `deployment/trial/Caddyfile`，本轮没有解除限制。

现有九项业务技能属于已登记、版本和摘要受校验的受管预设，通过固定业务工具与文件渲染器使用。新增原生 Skill 不会自动成为业务技能目录中的第十项，见 `internal/boyanskills/provider.go`、`internal/businessworkflow/skills_catalog.go`。

建议首先允许内部 Contributor 自建知识库与 Agent；新业务 Skill 采用“内部编写→审核→发布为新版本→授权给伙伴”的流程，保留现有运行约束。当前没有面向员工的完整网页草稿、审核、发布流程；初期可按项目 Skill 格式提交文件，由维护者审核、构建并安装新版本。若要求员工在网页直接自助创建和发布，需要再实现这一入口及权限，而不是宣称现已可用。

若确有原生代码型 Skill 开发需要，可单独设计内部研发空间与受控安装入口，验证沙箱网络及资源限制后再开放；伙伴入口维持现有受管业务技能。尚未选择或实施此方向。

## 验证与待决定项

本轮只读验证了路由门禁、同空间资源读取、技能运行方式和网关限制；没有创建内部员工或执行其写入请求，内部创建流程端到端为**未验证**。

后续在隔离测试环境验证：Contributor 创建知识库及 Agent，Viewer 创建请求被拒；Contributor 不能修改他人 Agent；伙伴无法读取新增内部知识库；原共享企业库仍可读；卡卡邀请的员工仍仅进入星辰；新增 Skill 发布后可被授权使用，未发布版本不可用。

需要人工验证：用独立内部员工与伙伴浏览器核对菜单、创建流程、资料范围和文件产出。若选择多个伙伴共用公共空间，还须先决定由总部统一邀请，还是开发按公司划分的多负责人及成员管理；不能沿用当前单负责人结构并宣称已按公司隔离。

尚需决定：是否继续要求刘伟健账号不能进入伙伴空间；是否保留伙伴负责人各自邀请员工。当前建议保留现有分公司空间和单一共享企业知识库，新增内部内容建设者权限，单独规划业务 Skill 发布流程。
